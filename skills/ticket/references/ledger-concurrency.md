# Ledger store: one writer per ticket by compare-and-set

## Problem

The ledger store writes a ticket's stamps, decisions, reviews and close through the ledger CLI, one subprocess per event. Earlier versions checked the ticket's newest event, then appended, then read the events back to see whether anything had landed in between. That check and that append were two calls, so another writer could always slip between them, and every repair (void notes, state restores, post-close read-backs) opened a new window. This design makes every write that matters one conditional append, makes the close two of them, and confirms each by its exit status alone.

## The CLI behaviour this rests on

Line numbers are in the ledger CLI's source (`skills/_lib/ledger/`) at commit `7dc929d`. Re-check them when the CLI changes.

- **L1. Compare-and-set.** `append` takes `--expect-revision <event id | none>` (`verbs/append.py:30`, parsed at `verbs/__init__.py:131-148`). The store runs the check inside the append's own transaction (`store.py:748-750`, inside `BEGIN IMMEDIATE` at `store.py:830`, before the insert at `store.py:886`): the append lands only if the item's newest event id equals the expected one (`store.py:516-526`). Otherwise it raises `StaleRevision` (`store.py:534-540`), whose message names the newest event's id, actor and session (`store.py:530-533`), and the CLI exits 5 with code `stale_revision` (`cli.py:165-166`, `verbs/__init__.py:27`). Nothing is written.
- **L2. Idempotency first.** The stored-key lookup runs before the precondition (`store.py:833-858`, then `store.py:859-860`). The same key with the same kind, payload, item and attribution (`store.py:482-513`) returns the stored event with exit 0 and no revision check; the same key with a different event raises `IdempotencyConflict` (`store.py:853-855`), exit 3 (`cli.py:163-164`). Keys are unique across the whole database (`migrations/0001_initial.sql:11`).
- **L3. `append` versus `state`.** `append` takes a caller's `--idempotency-key` and any payload the schema allows (`verbs/append.py:24-26`, `:50-60`). The `state` verb always generates a random key (`verbs/state.py:44`) and builds a payload of status, owner, claim and blocked-by only (`verbs/state.py:30-36`), so it cannot carry `source`.
- **L4. Revision from `query`.** `query --item K` reports `revision`, the id of the item's newest event of any kind, read in the same statement as the projection (`store.py:1050-1062`, `verbs/query.py:34-36`). Its item row has status, owner and claim but not blocked-by (`verbs/__init__.py:99-111`).
- **L5. `export-item` hides pass records.** `export-item` leaves out ephemeral events recorded before the item's latest close, and while the item is closed it leaves out all of them (`export.py:255-265`, `export.py:273-286`). `session.opened` and `session.closed` are ephemeral (`schema.py:409-410`); `item.state`, `item.note` and `item.stopped` are durable (`schema.py:393`, `:395`, `:397`) and always shown.
- **L6. Status is the latest state event.** An item's status is the payload of its newest `item.state` event (`migrations/0003_loop_writer_identity.sql:58-83`).
- **L7. Event ids are global.** The next id is the database tail plus one (`store.py:861-867`), so the event before C in an item's history is not id C − 1. Below, "the event before C" means the item's previous event.
- **L8. Exit 0 means committed.** The CLI prints success only after the insert's `COMMIT` (`store.py:910`, `cli.py:107-118`).
- **L9. Payloads.** `item.state` accepts an optional `reason` and `source` (`schema.py:83-95`); `item.stopped` requires `point` and `phase` and accepts `skills`, `refs` and `source` (`schema.py:349-360`); `close` is a phase (`schema.py:24`).

## Rules

The store's writer name W rides in each payload's `source`. "Pass P" is the pass id the store's `session.opened` claim carries.

1. **Held revision.** A store handle holds the ticket revision it has accounted for: the `revision` of `ledger --json query --item K` (L4), or `none` for a ticket with no events. It is never the largest id in `export-item`, which hides pass records on a closed item (L5): on a closed ticket whose newest event is a release, that id is permanently below the real revision and every conditional write from it would exit 5 forever. Only the handle's own successful appends advance the held revision.
2. **Pass ownership on every write but the release.** Before every write except a pass release (rule 6), the handle reads the ticket's events with `export-item` and refuses, writing nothing, when a pass is live that is not the handle's own (printing that pass's session id, host and start time), or when the handle holds a pass that is no longer live. A handle outside any pass may write only while no pass is live. Pass records are visible only while the ticket is not closed (L5), so no pass is ever claimed on a closed ticket (rule 5). The release is exempt because after the closed state lands `export-item` no longer shows the pass, so an ownership check would refuse the closing pass's own release.
3. **Conditional writes.** Every write except a pass release is one append with `--expect-revision <held revision>`: `write_stamp`, `record_decision`, `record_review`, `record_plan`, `record_tried`, the pass claim, the pending-close stamp and the closed state. On success the held revision becomes the new event's id. On exit 5 the store raises `TicketHeld` naming the writer of the newest event and writes nothing else except the pass's best-effort release (rule 6); the pass must re-read before writing again.
4. **Write keys.** Every conditional append carries a key unique to that logical write, generated once and reused only to retry that same write:
   - ordinary writes, the pending-close stamp included: `ticket-write/<ticket key>/<expected revision>/<kind>/<request token>`, with a random request token;
   - the closed state: `ticket-close/<ticket key>/<stamp event id>/<pass id>`, where the stamp is this close's pending-close stamp.
   Two independent handles writing from the same revision never share a key, so the second is refused by the revision check, not returned the first one's event as a retry (L2). Only one handle can have written a given stamp, so two closes never share a close key.
5. **Claim.** Starting a pass reads the ticket, refuses if any pass is live or the ticket's status is `closed`, and appends the `session.opened` claim (session id, host, started-at) with the expected revision it read. Two sessions racing from the same revision cannot both claim: the second append is refused and leaves no claim.
6. **Release.** Releasing a pass (after every close attempt, successful or refused, on the person's `release` command, or on an error exit) appends `session.closed` naming the pass, without a revision precondition or an ownership check (rule 2): giving up the ticket is safe whatever landed since, and it must succeed after the handle's revision has gone stale. Its key is `ticket-pass/<ticket key>/<pass id>/released`, so a retried release lands once.
7. **Close.** Pass P closes ticket K in exactly four steps.
   - (a) **Read.** `ledger --json query --item K` gives the held revision R (rule 1). `export-item K` confirms that P is the live pass and that the outward go is recorded, and gives the blocked-by list of the latest `item.state` event (L4: `query` does not report it). No write.
   - (b) **Pending-close stamp.** `ledger append --kind item.stopped --item K --expect-revision R --idempotency-key ticket-write/K/R/item.stopped/<token>` with payload `{point, phase: "close", skills, refs, source: W}`. It lands as event S. On exit 5 nothing was written: the store raises `TicketHeld` naming the writer, writes no stamp or state, makes the release (d), and the close stops there with the ticket open.
   - (c) **Closed state.** `ledger append --kind item.state --item K --expect-revision S --idempotency-key ticket-close/K/S/P` with payload `{status: "closed", owner, claim, blocked_by, source: W}`, owner and claim carried from (a)'s `query` row and blocked-by from (a)'s latest state event. It lands as event C. This is `append`, not the `state` verb, because `state` always generates its own random key and cannot carry `source` (L3): the close key and the writer name are exactly what resume checks (rule 8). Exit 0 is the confirmation (L8): the close is complete and nothing reads it back. On exit 5 nothing was written: the ticket stays open (or keeps whatever status the intervening writer set) with S as an orphan pending-close stamp; the store raises `TicketHeld`, writes no repair, makes the release (d), and resume reports the unconfirmed close and resumes at the outward go, and the next close writes a fresh stamp from a fresh read, so S is never reused.
   - (d) **Release.** `ledger append --kind session.closed --item K --idempotency-key ticket-pass/K/P/released`, with no precondition and no ownership check (rule 2). It runs after every close attempt that got past (a): after (c) lands, and after a refusal at (b) or (c). It is best effort: any failure is reported and ignored. It is safe after a refusal because it carries no precondition and only ends pass P: it changes no status, stop or decision, so it cannot overwrite what the other writer landed, and without it an open ticket would stay held by a pass that has already given up. After a successful close nothing reads it, because `export-item` hides the closed item's pass records (L5).
8. **Trusting a closed status on resume.** Resume reads the ticket (`query` and `export-item`) and decides before it claims anything. It trusts a close exactly when all of these hold:
   - the ticket's status is `closed`;
   - its latest `item.state` event C has idempotency key exactly `ticket-close/<ticket key>/<id of the event before C>/<pass id>`;
   - the event before C is an `item.stopped` with phase `close` whose `source` equals C's `source`;
   - that `item.stopped` is the ticket's latest `item.stopped`.
   Nothing else is checked. A trusted close is reported closed and no claim is taken. A ticket that is not closed is claimed (rule 5) and resumed from its card; when its latest `item.stopped` is a pending-close stamp with no close after it, resume reports the unconfirmed close and resumes at the outward go. A ticket whose status is `closed` but whose close is not trusted is reported with the first failed check and is not claimed (rule 5): the ledger hides pass records on a closed item (L5), so a pass held there would be invisible to every other writer. It stays as it is until its status changes.
9. **Ambiguous outcomes.** An unknown exit status, a crash, or an unparseable response does not prove the append did not commit. The store reads the ticket's events and looks for the write's exact key with the same kind and payload: found means it landed (the held revision becomes that event's id and the write returns normally; for (b), that id is S); absent means it did not, and the write raises `StoreUnavailable` with the CLI's output. A retry reuses the original key, which returns the stored event rather than exit 5 (L2). The store never retries a write under a new key. Rule 7's (d) is exempt: its failures are ignored.
10. **Old CLIs.** A ledger CLI that does not accept `--expect-revision` is refused at store selection with a one-line message naming the missing option.
11. **Deleted.** The read-back after every successful append, the close read-back, the close-void note, the state restore, and every post-close bookkeeping condition: balanced pass records after a close, the closing pass's own release as a condition of a valid close, and any repair of state after a refused close. The only read-back left is rule 9's lookup by key after an ambiguous outcome.

## What a trusted close ignores

A later `item.note` from anyone, appended after C, does not invalidate a trusted close; only a later `item.stopped` or `item.state` does, and rule 8 needs no clause for either because each is caught by "latest `item.stopped`" and "latest `item.state`". The reason: a note changes neither the ticket's status (L6) nor its resume point, which is the latest stop. Closed means the latest state says closed and that state is bound to this pass's latest stop; a note is commentary on a closed ticket and leaves both facts as they were. A later stop says work resumed after the close, and a later state says someone set a status since; either one means the close no longer describes the ticket. The same holds for every other kind that changes neither: a later link, decision or review does not invalidate the close. Later pass records are hidden on a closed item (L5) and no pass is claimed there (rule 5), so they need no rule either.

## Invariants

- Every event the store appends, except a pass release, was appended at exactly the revision the store last observed, by a handle that owned the live pass (or wrote while none was live).
- A close is two conditional appends confirmed by their exit statuses; after a refused one nothing is written but the pass's release.
- Every close attempt ends with the pass released (best effort), whatever its outcome.
- A closed status is trusted only under rule 8.
- No pass is claimed on a closed ticket.
- Fail-closed: a missing `--expect-revision` option is refused before any write; an ambiguous outcome is resolved only by finding the write's own key (rule 9), and is otherwise `StoreUnavailable`.

## Why the earlier review findings cannot recur

1. An outside `closed` state appended right after the pending-close stamp passed an adjacency-only check: rule 8 now requires C's key to bind the stamp's id and the pass, and C's `source` to equal the stamp's, which an outside writer's random-key `state` write cannot match.
2. A retry after a committed append looked stale, and an unparseable response was read as "not written": the CLI checks a stored key before the revision (L2), and rule 9 resolves every ambiguous outcome by the write's own key before deciding.
3. Two independent handles at the same revision shared a key, so the second was handed the first's event: every ordinary key carries a request token (rule 4), and a close key carries a stamp id that only one handle can have written.
4. Writes skipped the pass-ownership check, the close key had two forms, a later stop did not invalidate a close, and the invariant contradicted the unconditional release: rule 2 checks ownership on every write, rule 4 gives the one pass-suffixed close key, rule 8 requires the stamp to be the latest stop, and rules 3, 6 and the invariants exempt only the release.
5. Resume claimed a pass before validating, so its own claim invalidated every closed ticket: rule 8 decides before any claim, and a closed ticket is never claimed (rule 5).
6. Unbalanced pass records after a close left a live pass behind a trusted close: no pass is claimed on a closed ticket (rule 5), pass records there are hidden (L5), and rule 8 no longer reads them at all.
7. The test matrix required post-close pass pairs inconsistently with the rule: rule 8 has no post-close bookkeeping condition, so no test can contradict one; the tests below pin that pass records after C are irrelevant.
8. Requiring the closing pass's own release made every normal close fail its own read-back: the close has no read-back (rule 7 (c)), and the release (rule 7 (d)) comes after the close, is best effort, and is not a condition of trust.
9. Code review: the note-only repair let a raced `closed` state confirm a later retry, and the repair reported the wrong interleaved event: a refused close writes nothing, so no repair, void note or stale state of ours exists (rule 11); trust reads only the C-to-stamp binding (rule 8), and a refused close overwrote nothing, so there is no lost state to reconstruct.

## Tests

Each test names the production mutation that must turn it red.

- **Finding 1.** An outside writer appends `closed` (random key, via `state`) right after S, winning that revision: (c) exits 5, and resume reports the close untrusted, takes no claim and appends nothing. Mutation: drop the key check from rule 8.
- **Finding 2, retry.** The CLI commits (b) but its response is lost; the store retries with the same key and gets the stored event, not exit 5, and (c) then lands. Mutation: retry under a fresh request token.
- **Finding 2, ambiguous.** The CLI commits but returns unparseable output: the store finds the key, advances its revision, and the next write lands. With nothing committed, the key is absent, the write raises `StoreUnavailable`, and the revision is unchanged. Mutation: treat an unparseable response as not written without the key lookup; separately, treat an absent key as success.
- **Finding 3.** Two handles at the same revision issue the same kind of write with identical payloads: the first lands; the second is refused with `stale_revision`, never returned the first one's event. Mutation: drop the request token from the ordinary key.
- **Finding 4, ownership.** A fresh handle (no pass) writes after another pass has claimed the ticket: refused by rule 2, nothing written. Mutation: skip the pass-ownership check on one write.
- **Finding 4, close key.** A normal close stores C under exactly `ticket-close/<key>/<S id>/<pass id>`. Mutation: drop the pass suffix from the close key.
- **Finding 4, later stop.** A later `item.stopped` after a trusted close: resume no longer trusts the close. Mutation: drop the latest-stop check from rule 8.
- **Finding 4, release.** Release succeeds after the handle's revision has gone stale, and a retried release lands once. Mutation: add `--expect-revision` to the release.
- **Finding 5.** Resuming a validly closed ticket reports it closed and appends no claim. Mutation: claim before validating.
- **Finding 6.** Starting or resuming a pass on a ticket whose status is `closed`, trusted or not, appends no `session.opened`. Mutation: let rule 5 claim on a closed status.
- **Findings 7 and 8.** A close with no release after C, a close followed by the closing pass's release and another session's pair, and a close followed by an unmatched outside `session.opened` are all trusted. Mutation: require the closing pass's own release, or balanced pass records, in rule 8.
- **Finding 8, no read-back.** A normal close makes exactly two conditional appends and one release, reads the ticket only at (a), and completes when (d) fails. Mutation: read the card back after (c), or raise on a failed (d).
- **Code review, nothing written after a refused close.** After (c) exits 5 because an outside `item.state` and then an `item.note` landed between S and C, the store has appended only S and the release, and the ticket's status, owner and blocked-by are the outside state's. Mutation: append a void note on (c)'s exit 5; separately, drop `--expect-revision` from (c).
- **(b) exit 5.** An outside note lands after (a): (b) is refused, `TicketHeld` names that writer, the only event appended is the release, and (c) is never attempted. Mutation: continue to (c) after (b) exits 5, or accept exit 5 as success.
- **(c) exit 5.** An outside note lands between S and C: (c) is refused, the status is unchanged, and S is the latest stop. Mutation: drop `--expect-revision` from (c).
- **Orphan-stamp resume.** After (c)'s exit 5, resume reports the unconfirmed pending close, claims, and resumes at the outward go; the next close writes a fresh stamp S2 ≠ S from a fresh read and keys C on S2, and resume trusts it. Mutation: reuse the orphan stamp's id in the next close key instead of writing a fresh stamp.
- **Release after a successful close.** (c) lands, then `session.closed` under `ticket-pass/<key>/<pass id>/released` is appended although `export-item` no longer shows the pass. Mutation: apply rule 2's ownership check to the release, which refuses it once the ticket is closed.
- **Release after a refusal at (b).** (b) exits 5: the release lands, the ticket is open, and no pass is live, so a new session can claim it. Mutation: return from the refused close without the release.
- **Release after a refusal at (c).** (c) exits 5: the release lands, the ticket is open, no pass is live, and resume reports the orphan pending-close stamp and claims. Mutation: return from the refused close without the release, which leaves the pass live and makes the next resume refuse as held.
- **Outsider note.** An outside `item.note` appended after a trusted close: resume still trusts it and takes no claim. Mutation: invalidate a close on any later durable event.
- **Stale revision from export.** On a closed ticket whose newest event is the closing pass's release (hidden by `export-item`), the held revision equals `query`'s `revision`, and a conditional append at it lands. Mutation: take the held revision from the largest id in `export-item`, which exits 5 on every attempt.
- **Claim race.** Two sessions race to claim from the same revision: exactly one claim lands; the other leaves no claim. Mutation: claim without `--expect-revision`.
- **Old CLI.** A CLI without `--expect-revision` is refused at selection. Mutation: skip the capability check.
